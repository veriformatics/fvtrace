## Q3 — minimal runtime is a build experiment, not a guaranteed switch

[v4.35.0 CMake](https://github.com/leanprover/lean4/blob/v4.35.0/src/CMakeLists.txt#L353-L426) states: “LibUV does not compile on WebAssembly without modifications because building LibUV on a platform requires including stub implementations for features not present on the target platform. This patch includes the minimum amount of stub implementations needed for successfully running Lean on WebAssembly and using LibUV's temporary file support.” It then lists `uv__fs_event_close`, `uv__hrtime`, `uv__io_check_fd`, `uv__io_fork`, `uv__io_poll`, `uv__platform_invalidate_fd`, `uv__platform_loop_delete`, `uv__platform_loop_init` as undefined, and says: “Making additional LibUV features available on WebAssembly might require adapting the patch to include additional LibUV source files.”

OpenSSL is inside `if(NOT "${CMAKE_SYSTEM_NAME}" MATCHES "Emscripten")`. `if(NOT MULTI_THREAD)` prints “Disabled multi-thread support, it will not be safe to run multiple threads in parallel”; the same file's Emscripten block still supplies `-pthread`. Need to establish a single-thread runtime/standard-library closure rather than assuming flags compose.

[Upstream issue #15186](https://github.com/leanprover/lean4/issues/15186) reports initial v4.34.0 + emsdk 6.0.9 work: “I have built Lean for wasm at `v4.34.0` with emsdk 6.0.9 and `MULTI_THREAD=OFF` (which additionally needs #15172 and the two fixes in #14973 / PR #14974), and produced a working non-shared-memory bundle.” Initial tests only negated pthread at final link. **Read its later correction, not only the opening report**: [comment](https://github.com/leanprover/lean4/issues/15186#issuecomment-5854844291): “with no worker threads started, Chromium 153 and Firefox 155 both run the current shared-memory build on a page without COOP/COEP (the `SharedArrayBuffer` global is hidden, but `new WebAssembly.Memory({shared: true})` still works). So \"requires cross-origin isolation\" was wrong, at least for those two; I couldn't test WebKit.” Same comment: “What the gate still does, measured on v4.34.0: `MULTI_THREAD=OFF` then compiles the runtime without atomics/TLS and links non-shared memory, and a compiled test program passes in Node, Chromium and Firefox.” It also says: “`MULTI_THREAD=OFF` has no task manager, so the elaborator can't run there regardless.” These are author reports, not measurements made in this research; no literal file:// test is stated.

## Q5 — embed bytes; inspect the generated loader

- [Emscripten settings](https://emscripten.org/docs/tools_reference/settings_reference.html#single-file): `SINGLE_FILE`: “If set to 1, embeds all subresources (for example, the Wasm file) as strings in the generated JavaScript or HTML file.” Its worker note: “using a Worker requires the child-src directive to allow blob:”. `SINGLE_FILE_BINARY_ENCODE`: “If true, binary Wasm content is encoded using a custom UTF-8 embedding instead of base64”; “disable binary encoding with -sSINGLE_FILE_BINARY_ENCODE=0 to fall back to base64 encoding.” Thus single-file support does not inherently require a `data:` fetch; the produced loader determines that.
- [Same settings](https://emscripten.org/docs/tools_reference/settings_reference.html#dynamic-execution): `DYNAMIC_EXECUTION=0`: “we do not emit eval() and new Function()”; “the functions ccall() and cwrap() are still available, but they are restricted to only being able to call functions that have been exported in the Module object in advance.” Dynamic linking/`dlopen()` unavailable; use a static engine ABI, not a full compiler/interpreter plugin setup.
- [Module hook](https://emscripten.org/docs/api_reference/module.html#Module.instantiateWasm): “Module.instantiateWasm is an optional user-implemented callback function that the Emscripten runtime calls to perform the WebAssembly instantiation action”; accepts `imports`, `successCallback`. [MDN](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/instantiate_static): primary overload accepts “a typed array or `ArrayBuffer`”. **Inference:** embedded bytes passed to that overload avoid network/fetch/CORS entirely; need not use `instantiateStreaming`.
- `/home/eturkes/Projects/fvtrace/Fvtrace/Export.lean:134–136`: `default-src 'none'; script-src {← cspHash script};` and `require-trusted-types-for 'script'; trusted-types 'none'`. [MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src#unsafe_webassembly_execution): “The `'wasm-unsafe-eval'` source expression is more specific than `'unsafe-eval'` which permits both compilation (and instantiation) of WebAssembly and, for example, the use of the `eval` operation in JavaScript.” Adding the narrower token is distinct from permitting JS eval.
- [MDN Trusted Types](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/require-trusted-types-for): “control the data passed to DOM XSS sink functions, like `Element.innerHTML` setter”; “those functions only accept non-spoofable, typed values created by Trusted Type policies, and reject strings.” **Unconfirmed:** exact glue/worker compatibility with `trusted-types 'none'`. No direct source found asserting that this exact Emscripten loader + byte instantiation works under fvTrace's policy; searched MDN, W3C Trusted Types results, Emscripten Module/settings docs. MAIN owns the actual policy review.
- [MDN data URLs](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/data#common_problems): “Browsers are not required to support any particular maximum length of data. Chromium and Firefox limit `data` URLs to 512MB, and Safari (WebKit) limits them to 2048MB.” These are **data URL** limits, not inline `<script>`/local HTML guarantees. **No source found** for a general inline-script or file:// document-size ceiling in searched MDN/Chromium/Firefox results; memory, parse/startup time and generated loader behavior need measurement.
- [Emscripten pthreads docs](https://emscripten.org/docs/porting/pthreads.html): “Pthreads code will not work in deployed environment unless these headers are correctly set.” This addresses actual shared-memory threading; do not silently substitute it for a test of an idle shared-memory module (Q3 correction). Recommended experiment remains a thread-free static engine with no remote assets.
