# Kernel contract (U2) — tier `kernel`

Scope = the judgment-bearing core every surface (CLI, server, GUI, export) displays: trace decoding + well-formedness, effective statuses, claim states, ranking, experiments, plans, review state, sentences, the evaluation envelope. Proved in Lean 4.35 against `Fvtrace/Spec*` (human-read claims) where marked **proved**; the rest **tested** (red-first, or mutation credit). Gate = `lake build` (kernel check) + `fvtrace-trust` (axioms ⊆ `propext` · `Classical.choice` · `Quot.sound`; no escape hatch in a proof closure) + independent-kernel replay. `.agent/spec.md` Decisions bind; ids here (`D-*`, `WF-*`, `S-*`, `G*`) are cited by proofs + tests.

## Decode (D-*; tested + round-trip property)

- Input = UTF-8 JSON text. D-json: RFC 8259 syntax; duplicate object keys rejected; numbers = integers of ≤ 20 digits (the format's one number is `1`); nesting depth ≤ 64; size ≤ 16 MiB; parse time O(n log n) in the input (a trace can come from someone else). A trace file is opened only when regular (no FIFO, device or link to one) and refused by its size before a byte is read; at most one byte past the limit is read.
- D-shape: every object closed (unknown field ⇒ error); optional fields absent (never `null`); required fields listed below; enums exact lowercase strings. Defaults when absent: `experiments`, `exclusions`, `waivers`, `artifacts`, `trusts`, `requires` = `[]`; `failure` = `{}`; `latent` = `false`. Strings = Unicode scalar sequences: invalid UTF-8 and unpaired `\uD800`–`\uDFFF` escapes are rejected.
- D-id: ids match `^[A-Za-z][A-Za-z0-9_.-]{0,63}$`. D-text: text fields non-empty, contain no C0 control char except `\n`. D-date: `YYYY-MM-DD`. D-sha: 64 lowercase hex.
- Diagnostics = `{code, path (RFC 6901 pointer), message}`; decode errors stop the check (WF needs a decoded trace); every decode error found in one pass is reported. Exit codes (CLI): 0 = valid (warnings allowed), 1 = invalid trace, 2 = usage or I/O error.
- G-codec: `decode (encode t) = t` for every decoded trace; `encode` is canonical (D-canon).
- D-canon (review + statement digests): keys sorted by code point, no insignificant whitespace, strings escaped as ECMAScript `JSON.stringify` (`\"` `\\` `\b` `\f` `\n` `\r` `\t`, other C0 as `\u00xx` lowercase), non-ASCII raw UTF-8, integers in decimal.

## Model

- `Status` = `proved | checked | assumed | tested | open | violated`; `verified` = `{proved, checked}`; `asserted` = verified ∪ `{assumed}`.
- `Route` = `lean | runtime-checker | refinement | human-ruling | empirical`; `ceiling`: `lean` · `refinement` ↦ `proved`, `runtime-checker` ↦ `checked`, `human-ruling` · `empirical` ↦ `assumed`. `allowed r s` ⇔ `s ∈ {open, tested, violated, assumed}` ∨ `s = ceiling r`.
- `Kind` (fact) = `entailment | result | estimand | statistical | numerical | implementation | dataflow | provenance | interpretation | release | spec-review | instantiation`. Must-verify kinds `V` = `{entailment, result, estimand, numerical, implementation, dataflow}` (a claim may assume none of them); the rest = premise kinds (background conditions).
- Fact-level rule: `allows f s` ⇔ `allowed (route f) s` ∧ (`s ≠ assumed` ∨ `kind f ∉ V`). `ceiling f` = `tested` when `kind f ∈ V` ∧ `ceiling (route f) = assumed`, else `ceiling (route f)` (`allows f (ceiling f)` always holds). `Level` (claim) = `estimand | descriptive | inferential | causal | release`. `Effort` = `hours < days < weeks < months`; `ExpKind` = `dry | wet`.
- Trace `{fvtrace: 1, analysis, subjects, questions, facts, claims, experiments?, exclusions?, waivers?, review?}` (absent arrays = empty):
  - analysis `{id, title, summary, source?}`; subject `{id, title, kind: existing | prospective, createdBy?}`; question `{id, title, text}`.
  - fact `{id, subject, kind, text, status, route, evidence?, trusts?, instantiates?, why?}` (`why` = why a claim needs it, display text); evidence `{summary, artifacts?: [{path, sha256?, role?: text}], verifier?, statement?, statementDigest?, replay?: {command: [arg] (non-empty argv: program, then arguments, each a non-empty string without NUL; no shell), output?: sha}}`.
  - claim `{id, question, subject, level, text, headline?, needs: [F], entailment?: F, restates?: bool, latent?: bool, variantOf?}` (`text` = the exact statement; `headline` = its plain display form, never stronger: the reviewer's call); `needsAll c` = `needs ++ [entailment]` (`needs` alone for a restating claim). Default `restates` = `false`.
  - experiment `{id, subject, kind, effort, title, method, resources, success: {F: Status}, failure?: {F: Status}, requires?: [E], caveat}` (`resources` = prose; `requires` = experiments that must run first).
  - exclusion `{id, subject, between: [F, F], text, status, route, evidence?}` (a relation is itself a fact-like assertion: "these two cannot both hold").
  - waiver `{rule, claim, reason}`; review `{reviewer, date, digest, note?}`.
- Scenario = trace + `current : F ∪ X → Bool` (receipt binding, computed by the shell; consulted for recorded verified statuses alone) + overrides `ω : F ⇀ Status`.

## Well-formedness (WF-*; `check` = list of violations; **proved**: `check t = [] ↔ WF t`, each listed violation ⇒ its rule fails)

- WF-ids: ids unique across all collections. WF-refs: every reference resolves (question, subject, needs, entailment, variantOf, outcome keys, requires, exclusion pair + subject, createdBy, waiver claim, instantiates).
- WF-subject: claim needs + entailment, experiment outcome keys, exclusion pair all on the owner's subject; `instantiates` names a fact on another subject.
- WF-entail: a claim names `entailment` ⇔ ¬`restates`; an entailment fact has kind `entailment`, ∉ the claim's needs, used by exactly one claim; no `entailment` fact in any `needs`. A restating claim needs exactly one fact, of kind `result`, restated by no other claim.
- WF-needs: needs non-empty + duplicate-free.
- WF-route: every recorded fact status + every outcome status `allows`-ed by its fact (route + kind: no must-verify fact holds `assumed`); every exclusion status `allowed` by its route.
- WF-outcome: success non-empty, values ∈ asserted; failure values = `violated`; `requires` names experiments listed earlier on the experiment's subject (acyclic by construction: list prerequisites first).
- WF-receipt: recorded verified (fact or exclusion) ⇒ evidence with ≥1 artifact, every artifact with sha256, `verifier` + `statement` non-empty, `statementDigest` present.
- WF-path: artifact path non-empty, relative, `/`-separated, no `.` / `..` / empty segment, no backslash, no NUL.
- WF-prospective: `prospective` ⇔ `createdBy`; createdBy names an experiment on that subject; ≥1 `existing` subject; every fact on a prospective subject records `open` (its data does not exist yet).
- WF-variant: variantOf targets a claim on an existing subject; the variant's subject is prospective.
- WF-exclusion: the pair's facts differ; no duplicate unordered pair per subject.
- WF-consistent: no exclusion with recorded asserted status has both sides recorded asserted (a contradictory trace is an error, not a scenario).
- WF-waiver: rule ∈ lint ids; claim resolves; no duplicate (rule, claim).
- WF-kind: `instantiation` ⇔ `instantiates` present.

## Lints (warnings; a matching waiver suppresses + is listed with its reason)

- L-result: level ∈ {descriptive, inferential, causal} ∧ no `result` need. L-statistical: inferential | causal ∧ no `statistical` need. L-interpretation: causal ∧ no `interpretation` need. L-release: release ∧ no `release` need. L-estimand: estimand ∧ no `estimand` need.

## Receipts (shell computes `current`; tested against real files)

- statementDigest f = SHA-256 of D-canon `{id, subject, kind, text, route}` of f; for an entailment fact add its claim `{id, subject, level, text, needs: [{id, text}]}`; for a result fact a claim restates add `restatedBy` = that claim's `{id, subject, level, text}`; for an instantiation fact add the source fact's `{id, subject, kind, text}`. `why` + `headline` stay outside (display text; the review digest covers them). For an exclusion: `{id, subject, text, route, between: [{id, subject, kind, text} of each endpoint]}` (rewording an endpoint stales the relation's receipt).
- current x ⇔ every artifact exists under the project root + its sha256 matches ∧ statementDigest = the recomputed digest. Artifacts are read + hashed on every command; `--cached` (opt-in, disclosed) reuses a digest whose file kept its resolved path, size + mtime. Reasons (display): `changed`, `missing`, `statement-changed`. Path resolution never leaves the project root (symlinks resolved, then prefix-checked).
- Receipts are accepted as recorded (not replayed): the trusted base names receipt issuers.

## Replay (`fvtrace verify`, `pin --replay`; shell, **tested**; user rulings: in the project folder, pass = exit 0 + the pinned output)

- Domain = every fact (array order), then every exclusion (array order), whose evidence carries `replay`, whatever its status. Replays never feed `current`, a verdict, `check`, the envelope's judgments, `serve` or `export`: receipts stay digest-only.
- Opt-in: a command runs only under `fvtrace verify --run` or `fvtrace pin --replay`; `verify` alone lists each id + its command + whether `output` is pinned, runs nothing, rc 0; `--timeout` without `--run`/`--replay` = usage error (2); `--run`/`--replay` on any other command = usage error. `verify` (both forms) needs a decodable, well-formed trace (else rc 1, nothing runs); `pin --replay` keeps `pin`'s decode-only rule.
- Run (sequential, continuing past a failure): argv executed directly (no shell; the program found the way the OS finds it: `PATH`, or a path relative to the project folder), working folder = the project folder (the command, not fvTrace, may write there), environment inherited, stdin empty, stdout hashed as raw bytes as it streams (SHA-256, no decoding or newline normalization), stderr's last 4 KiB kept for display; each command printed (terminal-safe) before it runs (stderr under `--json`). `--timeout S` (whole seconds ≥ 1): once S seconds have passed since the start (checked every 20 ms; the kill lands within one poll interval plus scheduling delay), unless the process has exited and both pipes reached EOF, the process is killed (POSIX: its whole process group, started with `setsid`; Windows: the process alone, descendants may survive) ⇒ fail `timeout`.
- Pass ⇔ ¬timeout ∧ exit 0 ∧ `output` present ∧ sha256(stdout) = `output`. Fail reason, first match: `timeout`, `cannot start: …` (a spawn exception; a missing program may instead exit 255), `exit N`, `output not pinned`, `output changed`. A fail shows stderr's tail. `verify --run` rc: 0 every replay passes (or none exists) | 1 any fails | 2 usage or I/O.
- `pin --replay`: runs every replay first (each pass of exit 0 → new `output` = sha256(stdout); any other result keeps the old `output` and is reported), then pins every receipt digest (the replays may have rewritten artifacts), then writes the trace once; rc 1 when a replay or an artifact failed, else 0.
- `verify --json` → stdout = one document `{schema: "fvtrace.verify/1", trace, project, replays: [{id, command, pinned, ran, passed?, reasons}]}`.
- Security (MAIN ruling): a trace's commands run with the user's rights, only on the per-run opt-in; `verify` without `--run` shows them for reading first; the README says to run only commands of a trace you trust (a bundle carries its author's commands).
- Acceptance: a pinned fact whose verifier prints the statement it checks, the statement then weakened outside every pinned artifact ⇒ `check --json` reads every receipt current, `verify --run` fails (`output changed`, rc 1); no command starts without `--run` / `--replay` (a verifier that would create a marker file leaves none after `verify`, `pin`, `check`, `claims`, `export`). Self-trace: each proof fact replays `bash tools/statement.sh <Spec claim>` (`lake build` first, then `fvtrace-trust --statement`: a versioned, sorted dump of the claim's statement closure, core excluded); `maxRelevant` 20 → 0 in `Fvtrace/Engine.lean` alone keeps P6 + P7's receipts current and fails their replays.

## Effective status (S-*; total; **proved** lemmas)

- S-bind: `eff0 x` = `stale` if recorded verified ∧ ¬current x, else recorded. `EStatus` = `Status` + `stale`; strength `violated` 0 < `open` = `tested` = `stale` 1 < `assumed` 2 < `checked` = `proved` 3.
- S-override: `eff1 f` = `ω f` if defined, else `eff0 f` (a direct what-if may lower a status). ω valid ⇔ keys resolve to facts on existing or prospective subjects, once each ∧ `allows f (ω f)`; invalid ω rejected with diagnostics, never clamped or dropped.
- S-exclude: exclusion x with `verified (eff0 x)`: `verified (eff1 a)` ∧ ¬`asserted (eff1 b)` ⇒ `eff b = violated`, derivation witnesses = every such (x, a) (symmetric). Otherwise `eff f = eff1 f`. One pass: a derived violation asserts nothing, so derives nothing.
- S-conflict: x active ⇔ `asserted (eff0 x)` ∧ `asserted (eff1 a)` ∧ `asserted (eff1 b)`. `valid s` ⇔ no active exclusion on subject s.

## Claim state (S-state)

- mustVerify n ⇔ n names a fact with kind ∈ V (an id naming no fact: false).
- intrinsic c (on `eff`): `cannot` ⇔ ∃ n ∈ needsAll, `eff n = violated` ∨ ∃ asserted exclusion with both sides ∈ needsAll; `can` ⇔ ¬cannot ∧ ∀ n, verified (eff n); `conditional` ⇔ ¬cannot ∧ ¬can ∧ ∀ n, asserted (eff n) ∧ (mustVerify n ⇒ verified (eff n)); `open` otherwise. (The gate holds for any input; WF + valid ω keep every assumed need a premise kind, so on valid input it never fires: G13.)
- final c = `cannot` (reason `conflict`) if ¬valid (subject c), else intrinsic c.
- Breakdown (**proved** G2: an exact partition of needsAll, order kept): verified · premises (assumed, ¬mustVerify) · gaps (open | tested | stale, or assumed ∧ mustVerify) · blockers (violated, with recorded or derived witnesses); plus `incompatible` = asserted exclusions with both endpoints ∈ needsAll (with relation status) and `conflicts` = active exclusions on the subject. **Proved**: intrinsic cannot ⇔ blockers ≠ [] ∨ incompatible ≠ []; final cannot with reason conflict ⇔ conflicts ≠ [].
- mode = `recorded` ⇔ normalized ω = [] (keys sorted, duplicates rejected); else `what-if`. `supposed c` = needsAll with ω defined. `hypothetical c` ⇔ subject prospective ∨ ∃ n ∈ needsAll, eff n ≠ eff n under ω = ∅ ∨ valid (subject c) differs from its ω = ∅ value. `provisional` ⇔ review state ≠ `reviewed`.
- Counts = final states over claims on existing subjects (zero-filled keys can · conditional · open · cannot); per prospective subject apart.

## Sentences (engine-owned; **proved** G6)

- Claim + premise texts emitted verbatim (no case or punctuation change). can: `text`; conditional: `Assuming “p₁”; “p₂”: text` (premises in needsAll order); open / cannot: `text` with the verdict word beside it.
- Verdict words: can = `Fully supported`, conditional = `Conditional`, open = `Pending verification`, cannot = `Claim not possible`.
- Label = verdict word + qualifier list: `what-if` (hypothetical), `draft` | `stale review` (provisional), `if <creator title> runs` (prospective; the envelope carries the token `if-creator-runs` + `label.creator` = the creator's id, V-env), `conflicting what-if` (reason conflict).
- G6: a conditional sentence contains every premise text + the claim text verbatim; the emitted label's verdict word is `Fully supported` only for final = can.

## Ranking + blockers

- closable f ⇔ `eff f ≠ violated` ∧ strength (eff f) < strength (ceiling f). gates f = claims with f ∈ needsAll. unlocks f = gates f with final ∈ {open, cannot} whose final under `ω[f ↦ ceiling f]` ∈ {can, conditional}.
- work = every closable fact gating ≥1 claim, ordered |unlocks| desc, |gates| desc, id asc; **proved**: complete, duplicate-free, sorted, each entry's unlocks = the defining set. blockers = facts with `eff = violated` + the claims they block.

## Experiments

- closure E = the least set ⊇ E holding, for each member, its `requires` + the creator of its subject when prospective (a fixed point: a creator's own `requires` are included). merged P = per fact, the strongest asserted value any success in P sets. Applying a success never weakens: ω ⊕ P = per fact the strength join (max) of `eff1` and merged P; a failure sets its facts `violated`.
- preview e (success) = scenario ω ⊕ merged (closure {e}); preview e (failure) = ω ⊕ failure e. moves = claims whose final differs; lights = moves up into {can, conditional}; clears = cannot → open; breaks = failure moves into cannot. contingent ⇔ the success closure touches a `result` fact; applied ⇔ ω ⊇ merged (closure {e}). lowers = success moves down in rank; raises = the overrides the success applies (merged values stronger than `eff1`). Order: lights desc, clears desc, effort asc, id asc. **Proved** G3 (`MovesExact`): moves = exactly the replayed differences; G3b (`CountsPartition`): lights + clears + lowers = |moves| (each move counted once). breaks = a definition over failure moves (tested). Outcome isolation = WF-subject + G7. The envelope carries each experiment's counts + flags (P-rows); its closure, raises + moves = V-details.

## Plans (per claim with final ≠ can)

- Relevant R = experiments on the claim's subject whose success raises a needsAll fact above its `eff1` (strength up). Candidates = closure S for every S ⊆ R. coherent P ⇔ valid (subject) under ω ⊕ P.
- Result (tagged; first matching branch): `inconsistent` (ω already invalid on the subject) | `tooLarge` (|R| > 20: no plan claimed) | `noImprovement` (no coherent candidate beats the empty plan) | `planned P` (max rank of final under ω ⊕ P over coherent candidates; tie → min cost = effort counts months→hours lexicographic; tie → id list lexicographic). Every variant carries the coverage payload: remaining premises + gaps under the current scenario, uncovered needs (no member of R raises them; route hint), alternatives per need (experiment, status); `planned` adds experiments, final state, its premises + gaps under ω ⊕ P, contingent.
- Search = branch and bound over R in trace order, from the empty plan: each experiment first left out of the seeds, then put in (seeds, not executions: a closure may still add a left-out experiment as a prerequisite or creator); node = (seeds I, still open A); leaf candidate = closure I when coherent, folded by the plan order. Skip a node ⇔ closure I already conflicts (more successes keep every conflict) ∨ rank bound < rank B ∨ (rank bound = rank B ∧ cost B <lex cost (closure I)), B = the best so far; bound = the claim's state under ω ⊕ closure (I ∪ A) read on `eff1` (derived violations + subject conflicts only lower a state; the `incompatible` test stays, no success changes it) ⇒ no leaf below ranks higher or, at equal rank, costs less: every skipped leaf loses to B. Closure stops at its first fixed point (a step that adds nothing repeats). Worst case still 2^|R| leaves (a bound that exclusions defeat without a conflict); |R| ≤ 20 (Decisions).
- **Proved** G4: P closed + coherent + its reported state = replay (G4a); ∀ closed coherent Q (any experiments): rank Q ≤ rank P, equal rank ⇒ Q not strictly cheaper; `noImprovement` ⇒ no closed coherent Q beats the current state (G4b). Pruning lemma: with join application, experiments outside R never raise the claim's rank, so Q's stand-in = closure (Q ∩ R) ⊆ Q, a candidate at least as high + no costlier. **Proved**: the search = the exhaustive fold over every S ⊆ R (`search_eq`, `best_eq_ref`) ⇒ the same plan, ids included. The envelope carries `result` (+ `state`); the whole result = V-details. Measured (native `fvtrace plan`, 20 relevant experiments): each proving one need + the reasoning fact (one need each | one shared need | two per need) or a fact whose success makes every non-empty set conflict: ≤ 0.03 s; each proving 1–3 of 8 needs + the reasoning fact: 0.13–0.25 s (the exhaustive fold: 72 s at 20, 10–14 s at 16).

## Review

- digest t = SHA-256 of D-canon of t without `review`. state = `draft` (absent) | `stale` (digest ≠) | `reviewed`. Review covers the recorded trace alone; what-ifs are never reviewed evidence.

## Evaluation envelope (`fvtrace.evaluation/2`; CLI `--json` projections + server + export share it)

- V-env `{schema, mode: recorded | what-if, overrides: [{fact, status}] (normalized, sorted), trace: {digest, review: {state, reviewer?, date?}}, analysis, subjects: [{id, title, kind, valid, conflicts}], counts: {can, conditional, open, cannot}, prospectiveCounts: [{subject, counts}], questions, facts, claims, work: [{fact, unlocks, gates}], blockers: [{fact, claims}], experiments, exclusions: [{id, subject, between, text, recorded, effective, active}], lints: [{rule, claim, path, message, waived?}], actions}`; every member not named below = v1's, byte for byte (`tools/compare.sh` transform: V-cli).
- fact = `{id, subject, kind, text, route, recorded, effective, ceiling, closable, supposed, derivedFrom: [{exclusion, source}], trusts, instantiates?, why?, evidence?, receipt?: {current, reasons}}`; `ceiling` = `ceiling f` (§ Model: the status `suppose f` sets), new in v2.
- claim = `{id, question, subject, level, text, headline?, latent, needs, entailment?, restates, final, intrinsic, label: {verdict, qualifiers, creator?}, verified, premises, gaps, blockers, incompatibleCount, hypothetical, provisional, plan, variantOf?}` (user rulings: envelope lists on request): v1 − `conflicts` (= its subject's `conflicts`, one copy per subject) − `sentence` − `incompatible` (both → V-details; `incompatibleCount` = the list's length, so intrinsic cannot ⇔ blockers ≠ [] ∨ incompatibleCount > 0 stays readable); the prospective qualifier = the token `if-creator-runs` in its v1 position, with `label.creator` = the creating experiment's id (v1: `if <creator title> runs`; the GUI shows the title, the CLI text keeps it); plan = `{result}` + `state` when `planned` (coverage + the planned members → V-details).
- experiment = `{id, subject, kind, effort, title, method, resources, caveat, success, failure, requires, applied, contingent, prospective, creates, lights, clears, lowers, breaks}`: v1 − `closure`, `raises`, `wins`, `losses` (→ V-details).
- action = `{id, kind, target}`: the one-click domain from the evaluated scenario, ids + order = v1's (`suppose:f` for closable f, `success:e`, `failure:e` for a non-empty failure, `plan:c` for a planned result); its what-if = V-action (a click sends the reference; served GUI: the server expands, exported page: its engine).
- Size (P-bytes): linear in the trace: each member is bounded by an input list (needs, outcomes, exclusions per fact, waivers) or by one per record; no text repeats per claim (a claim's own words + ids alone); every cross-product list (closures, moves, plans, alternatives, excluded pairs, sentences, raisers) = V-details. Witness shapes beside the P-bound ones: all-pairs exclusions (n facts pairwise excluded, n claims needing all: v1 n³ `incompatible` entries) + one long premise needed by every claim; both linear in v2.
- V-action `expand ω A`: A not among the ids of `actions` under ω ⇒ problem `action`, message `"A" is not a suggested what-if`; else ω' = normalize (v1's complete what-if: `suppose f` ↦ ω ⊕ [f ↦ ceiling f], `success e` ↦ ω ⊕ raised (closure [e]), `failure e` ↦ ω ⊕ [each failure key ↦ violated], `plan c` ↦ ω ⊕ raised (the planned experiments); ⊕ = `withOverrides`: the action's keys replace ω's). `Evaluate.actionsWith` keeps computing these lists, for one action on request + as the test oracle. The answer at ω': `mode` = recorded iff ω' = [] (a success that raises nothing, from the recorded view), else what-if; `overrides` = ω'. In a WF trace, ω' is valid whenever ω is (Acceptance: Actions), so an expansion never yields a what-if problem there.
- V-details `fvtrace.details/1`, one item under ω (after any expansion): `{schema, mode, overrides, trace, item, …}` (`mode`, `overrides`, `trace` = the envelope's at that ω). item = `KIND:ID`: `experiment:E` ↦ `closure`, `raises`, `wins`, `losses` (v1's experiment members: same values, order + forms); `claim:C` ↦ `sentence` (v1's), `incompatible` (v1's list) + `plan` (v1's full plan object: `result`, `premises`, `gaps`, `uncovered`, `alternatives` + for `planned`: `experiments`, `state`, `planPremises`, `planGaps`, `contingent`); `fact:F` ↦ `raisedBy` = the ids, in `experiments` order (multiplicity kept), of the experiments whose `raises` names F (the list v1's GUI derived). Problem `item`: `"X" is not of the form KIND:ID` (no `:`, an empty side, or a kind outside experiment · claim · fact); `"E9" is not an experiment on record` · `"C9" is not a claim on record` · `"F9" is not a fact on record` (first match by id, as every lookup). Cost = one item's lists (one closure + its moves, one plan, one reverse reachability: P-raisers), never the whole envelope's.
- V-request (one request form for every surface): `{whatif: string, action?: string, details?: string}` (exactly these keys, string values; anything else ⇒ problem `invalid`, `the request is not of the form {whatif, action?, details?}`), answered in this order: the what-if (`Overrides.parse`: problem `what-if`), then the action (V-action: problem `action`), then the item (V-details: problem `item`); answer = the details document when `details` is given, else the envelope at `expand ω A`.
- V-cli: every command taking `--whatif` takes `--action A` (the command runs at `expand ω A`); `fvtrace eval --details ITEM` prints the details document in place of the envelope. Problems keep today's transport: `fvtrace: <message>` + the usage text on stderr, exit 2, nothing on stdout. Projections: `claims --json` = {schema, mode, overrides, trace, subjects, counts, claims}; `gaps --json` = {schema, mode, overrides, trace, work, blockers}; `experiments --json` = {schema, mode, overrides, trace, experiments}; `plan <c> --json` = {schema, mode, overrides, trace, claim, plan} (`claim` = the envelope's claim c, `plan` = its details' full plan). Text output (`claims`, `gaps`, `experiments`, `plan`, `check`, `review`, `verify`) unchanged, byte for byte.
- V-complete (user ruling: batch path): `fvtrace eval --complete` (with `--whatif` / `--action` as `eval`) prints `{schema: "fvtrace.complete/1", envelope, items: [{item, …}]}` = the envelope + the V-details payload of every item, one header for all: each experiment (envelope order), then each claim, then each fact (trace order); opt-in, its output grows with the lists by design (P-time exemption: only its emitting); `--complete` + `--details` = usage error. Oracle: its lists = v1's (experiment lists, full plans, sentences, `incompatible`, derived `raisedBy`).
- Parity: a successful answer (envelope or details) is byte-equal across `fvtrace eval [--whatif ω] [--action A] [--details I]` stdout, the server's body and the page engine's answer for the same request on the same snapshot (trace bytes, bindings); projections = the envelope's same keys, structurally (`plan --json`'s `plan` = the details' `plan`). A refusal agrees in kind + message across the three (the CLI prints the message after `fvtrace: `, the server + page answer `{problem: {kind, message}}`).

- V-serve: one data route `POST /api/answer`, body = a V-request (JSON, ≤ 16 MiB + 1 KiB: larger ⇒ 413 before any parse), answer = the envelope, the details or a problem; GUI files stay `GET`. Access order (`Server.decide`, before any I/O): method (`POST` on `/api/answer`, `GET` elsewhere: 405), `Host` (421), path (404), token (403: no request without it reaches a parser or the body), then the body. No CORS: a page from another origin cannot send `Authorization` (or a JSON body) without a preflight, and `OPTIONS` answers 405. Problems answer 400 (`invalid`, `what-if`, `action`, `item`) or 409 (`view`, below; the trace problems as today). View identity (served only; the snapshot never changes): each answer carries header `X-Fvtrace-View` = hex SHA-256 of D-canon `{trace: sha256 of the trace bytes, bindings: [{id, current, reasons}], overrides: ω'}`; a request may send `X-Fvtrace-View`, and when the state it would answer from differs, the answer is 409 `{problem: {kind: "view", message: "The claims or their evidence changed, so this page shows them again."}}` (the GUI re-evaluates, then asks again). The GET evaluation route retires with v1. A request = the CLI's answer for the same request (Parity), through P-cache.

## GUI responsiveness (U-*; user ruling GUI responsiveness; served + exported; display only: `.claude/rules/web.md`)

- U-lookups: the GUI builds its id maps (facts, claims, experiments, exclusions, subjects, actions) once per envelope it adopts; no card, contact or row scans a whole envelope list (v1: each card rebuilt a fact map twice + each contact scanned every action ⇒ cards × facts time + memory: 5,000 claims = 2.2 GiB of heap, the tab crashed on the next click).
- U-select: a selection moves the highlight + fills the details panel; the board is not rebuilt (every card element stays the same node: e2e identity check). The panel's summary parts (the envelope's own fields) show at once; its detail sections (V-details) stay absent until the details answer for the shown view arrives (panel `aria-busy`, no placeholder text), re-requested after each new evaluation while an item is selected; an answer for another view (its `overrides`, or served its view header, differ) or an older request (U-coalesce) is dropped; a 409 `view` answer re-evaluates the view first.
- U-update: an adopted envelope replaces only the cards whose inputs changed (the envelope fields a card reads differ between the old envelope and the new one); unchanged cards keep their nodes (e2e identity check); order + groups follow the new envelope.
- U-long: a list the GUI draws (cards on the board, a card's contacts + condition lines, a details list) renders what the interaction's budget holds and the rest as it comes near the viewport; the whole list stays reachable by scrolling; a selected or focused item renders first. The look of a long list = the GUI unit's design call (screenshots for the user; `CLAUDE.md` UI design).
- U-busy: each request paints the busy state (body `aria-busy` ⇒ `cursor: progress`) before any engine work: served = the request is asynchronous; exported = the engine works in its Worker. A request still running after 1 s also shows a visible indicator (touch screens draw no cursor; Nielsen: past 1 s, show that the computer is working), hidden when the answer arrives; reduced motion honored.
- U-coalesce: requests carry a monotonic number; an answer older than the newest request of its kind (evaluation; details per item + view) is dropped, so A → B → A never shows the first A. At most one evaluation request is in flight; a newer one waits + replaces any older waiting one.
