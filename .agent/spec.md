## Intent

fvTrace is a tool to help analyzers of scientific data understand what claims they can and cannot make. In this context, "fv" is short for "formal verification". We take the stance that a claim can only be made if it is formally verified. In any existing analysis, where no formal verification work has been performed yet, this tool can identify where such work can be applied, and if verified, what resultant claims can be made. This is the basic premise but it can be extended. In general, the tool should help users navigate what their scientific questions are, what gaps that need filling in order to answer those questions, and help ensure nothing is overstated. It can also be used to help identify directions and associated relationships that a user might have overlooked or understated, which become relevant if certain facts about the current analysis are true (or can be verified to be true).

Users will interact with fvTrace through a CLI and web-accessible GUI. If fvTrace will use LLM-inference to help accomplish its goals, it should come with instructions so that it can be used from within a user's existing coding agent session.

## Decisions

- Product = local OSS tool over one project folder (user ruling): reads the analysis (code, data, microscopy, manuscripts) and never writes into it; fvTrace's own files (trace, review record, digest cache) live in its data dir (`FVTRACE_HOME`, else the platform data dir `/fvtrace/<project>/`), `--trace` overrides. Writes land in the project only where the user points them (`--trace` naming a file there, `FVTRACE_HOME` or `skills install --dir` inside it, a replay command under `verify --run` / `pin --replay` (user ruling: replays run in the project folder; the command, not fvTrace, may write there)); `export` refuses destinations inside it. Hosted multi-user service = fvapi, a separate paid product in its own repo (user rulings: cloud builds, e.g. replays run remotely, belong there; fvapi = the library behind one API, hosted on vflab; fvTrace + fva gain the capability to call it for their normal work). Its plan sells compute past the local limits (user ruling): exact plan search past 20 relevant experiments, verifier replays, large what-if sweeps; each local limit stays named in one place so the service can raise it; nothing shipped mentions the service until it exists.
- Stack (user ruling: fvTrace must itself exemplify FV) = Lean 4.35 throughout: one native binary (engine, trace checker, CLI, local HTTP server on `Std.Http`). Kernel semantics proved in Lean against a human-readable spec module; gate = axiom audit + independent-kernel replay of every proof. Own JSON codec on `Std` (`Lean.Data.Json` links all of `Lean`: 118 MB binary, measured). SHA-256 = vendored HACL* verified C over FFI (pure Lean measured 13 MB/s vs coreutils 276 MB/s). GUI = no-build ES modules typed by JSDoc, display only: every verdict, ranking + plan it shows comes from the engine. Dev-only Node toolchain (TypeScript 7 checkJs, oxlint, Prettier, stylelint, html-validate, Playwright + axe).
- GUI access (user rulings, MAINTAIN security review: no cookie, since cookies ignore ports and so reach every server on the host; no link to click, no `127.0.0.1` or token in the address bar): `fvtrace serve` holds one port on both loopback addresses (`127.0.0.1` + `::1`: `localhost` names reach either) and opens the user's browser itself, through a private redirect page, at `http://fvtrace.localhost:8718/` (port 8718 = U+220E ∎, end of proof: an easter egg the help leaves unsaid); a per-run token rides in the link's `#` part, the page keeps it in its own origin's `localStorage` and sends it with each data request, the GUI files themselves load without it; every request names an allowed `Host` (DNS rebinding); the link is printed alone where the browser cannot be opened (`--no-browser`, SSH, WSL, no display) and, after an open, as a fallback line (MAIN, departing from the approved "printed only where the browser cannot be opened": an opener's exit 0 does not prove the page loaded; a Snap browser cannot read hidden folders, macOS may hand HTML files to another app); `--host` opts into LAN with the same token (printed link). Sharing (user ruling: both): `fvtrace export --html` = one self-contained page: the recorded verdicts precomputed + the engine compiled to WebAssembly, so any stacked what-if evaluates in the page (user rulings, IMPLEMENT export: recorded view + engine, per-action envelopes dropped; the engine is built during `lake build` from pinned Emscripten + Lean runtime sources, never committed; export note "This page was exported. It shows the evidence as it was at export, and its what-ifs run in your browser."; a browser that cannot run it keeps the recorded view: "This browser cannot run the what-ifs on this page, so it shows the facts as recorded."; the engine = the native engine's definitions compiled to WebAssembly: its trusted base adds Emscripten, the browser + the page's engine adapter, and its agreement with the native binary is tested (differential test), not proved); `--bundle` = trace + copies of its pinned evidence for a colleague's own `fvtrace serve`.
- Engine speed (user ruling, security review F5: the full fast engine): the binary answers through sorted indexes + memos, each proved equal to the definitions the other claims read (`Spec.LookupsAgree`, `Spec.SortMembersAgree`, `Spec.AnswersAgree`); bounds = kernel.md P-bound (Response time; `tools/scale.sh --assert`, idle host); output that grows by design (`eval --complete`; the cross-product lists, served per item as details; `gaps` text on one claim with thousands of open needs, user ruling: exempt, as real traces carry tens) stays exempt (kernel.md P-bytes, V-complete, P-time); law = `.claude/rules/fast.md`.
- Capability first (user ruling, IMPLEMENT what-ifs by reference): laptop usability is a goal, never a cap on what fvTrace can do (the hosted plan sells compute past local limits) ⇒ the local targets below (Response time, Memory, GUI responsiveness) shape how it computes, not what it computes: anything that leaves the envelope stays computable on request (CLI, server, page engine); local limits stay named constants the hosted service can raise; one feature may have more than one processing path (laptop, browser, hosted).
- Response time (user ruling, IMPLEMENT what-ifs by reference; supersedes the 60 s in Engine speed): every user-facing time bound follows Nielsen's three response-time limits (nngroup.com/articles/response-times-3-important-limits/): 0.1 s = feels instantaneous (a click's own feedback); 1 s = flow of thought kept (past it, show that the computer is working); 10 s = attention kept (past it, a percent-done indicator + a clearly signposted way to interrupt).
- GUI responsiveness (user ruling, IMPLEMENT what-ifs by reference): the GUI builds its lookups once per envelope, updates only what a click changes (a selection moves the highlight + fills the details; a what-if replaces only the cards whose content changed) and renders long lists as they scroll into view; the server keeps the loaded trace + the last answer in memory (reloaded when the trace or its evidence changes) and evaluates the recorded view at launch; the exported page's engine decodes its snapshot once + keeps the last answer. Bounds (Response time), served + exported, up to the 16 MiB cap: a selection shows within 0.1 s; details arrive within 1 s (graded for a claim + an experiment, user ruling); a what-if or action shows its busy state within 0.1 s + its result within 10 s; long lists show their size above them and, when a reader outruns their mounting, an end line ("Showing 34 of 300 claims. More appear as you scroll."); the find route = the field "Find a claim, fact or experiment" over the board (exact id, then id prefix, then words; up to 20 matches; Enter takes the first) (user rulings, IMPLEMENT what-ifs by reference: look + form shown, count lines added, form kept); timings come from the reference host, a pool host measured while no other job holds it (user rulings: the run waits for it; `CLAUDE.local.md` names it); the GUI's memory = its live JS memory after a collection (user ruling).
- Prerequisite chains (user ruling, IMPLEMENT what-ifs by reference: speed work over a local limit or progress + Stop): exact rankings + plans stay; the closure pass is rebuilt aiming at linear time on chains + stars, graded on `tools/scale.mjs prereqs` at its cap by the Response time bound; general prerequisite structures may stay super-linear (ungraded, like F5's other shapes); a failed attempt goes back to the user.
- Envelope lists on request (user rulings, IMPLEMENT what-ifs by reference, under Capability first): a claim's excluded need pairs (`incompatible`) + its "Assuming …" sentence live in its details; the envelope carries the pairs' count, and a card on screen with pairs names them once its details arrive (the card wording stays); the prospective qualifier names the creating experiment by id, the GUI showing its title; `fvtrace claims` keeps printing sentences + titles.
- Batch path (user ruling, IMPLEMENT what-ifs by reference): `fvtrace eval --complete` = the envelope + every item's details in one document, opt-in, for agents + large machines; its output grows with the lists by design.
- Exported page engine in a Worker (user ruling, IMPLEMENT what-ifs by reference, over keeping it on the page's thread): the page stays responsive while its engine works (selections within 0.1 s during start-up + evaluations); the page's CSP adds `worker-src blob:` + one named Trusted Types policy that accepts only the page's own worker, beside `'wasm-unsafe-eval'`.
- Exported page without WebAssembly (user ruling, IMPLEMENT what-ifs by reference): engine only, the page linear in size; the recorded verdicts + lists show, and each detail section that needs the engine says "This browser cannot run the what-ifs on this page, so it cannot show these details."
- Memory (user rulings, IMPLEMENT what-ifs by reference; the cap raised from 1.25: allocator noise): RSS ≤ 2.5× per doubling of n + at the 16 MiB cap ≤ 1.5 × the worst `eval` RSS among the F5 shapes (wide, deep, experiments, exclusions; same binary), for `eval` + one `serve` evaluation on `outcomes` + `prereqs` and `eval` on `whatif`.
- Trace format = JSON (`"fvtrace": 1`) + JSON Schema printed by `fvtrace schema` (MAIN ruling: a YAML parser would enlarge the verified binary's trusted base).
- Trace model = questions → claims → facts + subjects + experiments + exclusions + waivers + review (JSON keys `facts`, `claims`, …). Fact = one statement + `kind` + `status` + `route` (`lean`, `runtime-checker`, `refinement`, `human-ruling`, `empirical`; route ceiling: `proved` needs `lean` | `refinement`, `checked` needs `runtime-checker`, the rest top out at `assumed`, or `tested` for a must-verify kind) + evidence + trusted base + subject + optional `why`. Claim = `text` (the exact statement) + optional `headline` + optional `restates`. Contract = `.agent/contracts/kernel.md`.
- FV stance: verified = `proved` | `checked` (proved checker accepted the actual object). `assumed` = declared premise ⇒ claim only in conditional form. `tested` | `open` = gaps. `violated` ⇒ claim cannot be made as written.
- Only background conditions may be assumed (user rulings, IMPLEMENT GUI): must-verify kinds = entailment (Reasoning), result, estimand (Measurement), numerical (Calculation), implementation, dataflow (Data flow) never hold `assumed`: recorded or in an experiment outcome = `fvtrace check` error, in a what-if = rejected. Assumable kinds = statistical, provenance, interpretation, release, spec-review, instantiation. The engine's Conditional rule demands every must-verify need verified as well (holds for any input; the input rule keeps it from ever firing, so the key's Assumed → Conditional pairing + "A fact it needs is still open." stay exact).
- Claim state = `cannot` (a need violated, incl. derived; needs both sides of an exclusion; or a conflicting scenario) > `can` (every need verified) > `conditional` (every must-verify need verified, the rest assumed) > `open`. Verdict words (user ruling, round 2, every surface: GUI, CLI, export, engine labels + the proof naming `Can claim`) = Fully supported (can) / Conditional (conditional) / Pending verification (open) / Claim not possible (cannot) (user's set, chosen over MAIN's "Needs verification" + "Not possible as worded"); fact state `assumed` displays as "Assumed" (user ruling, round 2: the fact is assumed, the claim conditional).
- Conditional = reasoning verified (user rulings, round 2 + IMPLEMENT GUI, supersede the entailment ruling's "human-ruled entailment = assumed ⇒ at most On assumption"): a claim reads Conditional only when every need of a must-verify kind (its entailment fact, every `result`, measurement, calculation, implementation + data-flow fact) is verified (`proved` | `checked`); only premises (background conditions specific to the analysis, e.g. random assignment, independent samples) may stand as assumptions; otherwise Pending verification. A judgment mixed into a reasoning step → reword the claim to what can be proved, or split out a substantive, contestable premise (never one restating "the conclusion follows"). Universal premises (records honest, instruments working, labels right; for fvTrace's own claims, the compilers + runtime that run the proved code) are no claim's facts: the review sign-off vouches for them once (user rulings, round 2 + IMPLEMENT: listing them per claim = busy work). A claim that restates one checked result needs no separate reasoning fact (user ruling, round 2): `"restates": true`, `needs` = that one `result` fact, no `entailment` (MAIN ruling on the format).
- Headline + exact statement (user request, round 2: claims too wordy): a claim shows a plain headline; its exact statement (= what the proofs cover, the claim `text`) opens on request ("Show the exact statement"; shown in full in its details). Rule: the headline never says more than the exact statement; the reviewer confirms that at sign-off. MAIN rulings: `headline` + `why` stay outside statement digests (the review digest covers them); the CLI prints the exact sentence, `--json` carries both; `fvtrace review` prints what the sign-off vouches for (headlines say no more than their exact statements + the universal premises).
- Entailment (user ruling: strict): every claim but a restating one names one entailment fact ("these needs entail the sentence as worded"), counted as a need; unverified, it holds the claim at Pending verification at best.
- Evidence binding (user ruling): `proved` | `checked` require a receipt = artifacts (project-relative path + sha256) + verifier + statement + a digest of the fact's own content (an entailment fact's covers its claim's text + needs; a restated result's covers its restating claim's text) ⇒ an artifact changed or missing, or the fact or claim reworded since pinning ⇒ effective status `stale` (unverified, shown beside the recorded status); `fvtrace pin` records digests; receipts are accepted, not replayed (trusted base). Replay (user rulings): evidence may name a verifier command (`replay`, argv, no shell); `fvtrace verify --run` re-runs it in the project folder and passes on exit 0 + the output digest `pin --replay` recorded (catches a statement weakened outside the pinned files); nothing runs without `--run` / `--replay`; a replay never changes a verdict. Every surface shows the engine's label (recorded | what-if, review state, prospective qualifier) + its sentence where that surface prints sentences (`fvtrace claims`, claim details); claim + fact texts appear verbatim.
- Subjects (user ruling): every fact + claim binds to a subject (the existing analysis or a dataset/analysis an experiment would create); an experiment's outcomes touch only its subject's facts ⇒ a new-data experiment lights sibling claims, never existing ones; cross-subject reuse = an explicit instantiation fact.
- Exclusions (user ruling): an exclusion = two facts that cannot both hold on one subject, itself carrying status + route + evidence; only a verified exclusion derives a violation (from a verified side); a recorded contradiction (asserted exclusion + both sides asserted) = `fvtrace check` error; a what-if asserting both sides ⇒ every claim on that subject reads Claim not possible (`conflicting what-if`); a claim needing both sides ⇒ cannot.
- Results + lints (user ruling): kind `result` = the observed value/pattern a claim asserts; `fvtrace check` warns per claim level (estimand, descriptive, inferential, causal, release) on missing roles, suppressed only by a recorded waiver with reason.
- Where FV pays = per closable fact (not violated): claims it gates + claims verifying it alone unlocks, ranked by unlocks; violated facts list apart as blockers (reword or new data). `latent` claims = overlooked directions.
- Experiments: `kind` `dry` | `wet`, `effort` hours < days < weeks < months, `success` (asserting statuses only) + `failure` (`violated` only) replayed as what-ifs on the experiment's subject, closed over `requires` + the creator of a prospective subject; per experiment `lights` (claims raised into can | conditional), `clears` (cannot → open), `breaks` (failure → cannot); ranked lights > clears > cheaper. A success touching a `result` fact reads "if this result is observed".
- Experiment outcome honesty (scientist-1 rulings): `checked` only via a proved checker on the actual data, `proved` only via a completed proof; empirical support → `assumed` at most for a background condition, nothing for a must-verify fact (no success outcome reaches it; record `tested`); failure = established counterexample, inconclusive → `{}`.
- Plans (user ruling): per claim, a coherent experiment set (one subject, prerequisite-closed, no conflict) reaching the highest state the suggestions allow, cheapest by ordinal effort among those (exact search; above 20 relevant experiments the result is `tooLarge`, no plan claimed); alternatives per fact + remaining premises listed; labelled coverage, never scientific priority.
