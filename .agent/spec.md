## Intent

fvTrace is a tool to help analyzers of scientific data understand what claims they can and cannot make. In this context, "fv" is short for "formal verification". We take the stance that a claim can only be made if it is formally verified. In any existing analysis, where no formal verification work has been performed yet, this tool can identify where such work can be applied, and if verified, what resultant claims can be made. This is the basic premise but it can be extended. In general, the tool should help users navigate what their scientific questions are, what gaps that need filling in order to answer those questions, and help ensure nothing is overstated. It can also be used to help identify directions and associated relationships that a user might have overlooked or understated, which become relevant if certain facts about the current analysis are true (or can be verified to be true).

Users will interact with fvTrace through a CLI and web-accessible GUI. If fvTrace will use LLM-inference to help accomplish its goals, it should come with instructions so that it can be used from within a user's existing coding agent session.

## Decisions

- Product = local OSS tool over one project folder (user ruling): reads the analysis (code, data, microscopy, manuscripts) and never writes into it; fvTrace's own files (trace, review record, digest cache) live in its data dir (`FVTRACE_HOME`, else the platform data dir `/fvtrace/<project>/`), `--trace` overrides. Writes land in the project only where the user points them (`--trace` naming a file there, `FVTRACE_HOME` or `skills install --dir` inside it); `export` refuses destinations inside it. Hosted multi-user service = separate paid product, other repo.
- Stack (user ruling: fvTrace must itself exemplify FV) = Lean 4.35 throughout: one native binary (engine, trace checker, CLI, local HTTP server on `Std.Http`). Kernel semantics proved in Lean against a human-readable spec module; gate = axiom audit + independent-kernel replay of every proof. Own JSON codec on `Std` (`Lean.Data.Json` links all of `Lean`: 118 MB binary, measured). SHA-256 = vendored HACL* verified C over FFI (pure Lean measured 13 MB/s vs coreutils 276 MB/s). GUI = no-build ES modules typed by JSDoc, display only: every verdict, ranking + plan it shows comes from the engine. Dev-only Node toolchain (TypeScript 7 checkJs, oxlint, Prettier, stylelint, html-validate, Playwright + axe).
- GUI access: `fvtrace serve` binds loopback with a per-run token (cookie after first load) + Host allowlist; `--host` opts into LAN with the same token. Sharing (user ruling: both): `fvtrace export --html` = one self-contained page, verdicts + every one-click what-if precomputed by the engine; `--bundle` = trace + copies of its pinned evidence for a colleague's own `fvtrace serve`.
- Trace format = JSON (`"fvtrace": 1`) + JSON Schema printed by `fvtrace schema` (MAIN ruling: a YAML parser would enlarge the verified binary's trusted base).
- Trace model = questions → claims → facts + subjects + experiments + exclusions + waivers + review (JSON keys `facts`, `claims`, …). Fact = one statement + `kind` + `status` + `route` (`lean`, `runtime-checker`, `refinement`, `human-ruling`, `empirical`; route ceiling: `proved` needs `lean` | `refinement`, `checked` needs `runtime-checker`, the rest top out at `assumed`) + evidence + trusted base + subject. Contract = `.agent/contracts/kernel.md`.
- FV stance: verified = `proved` | `checked` (proved checker accepted the actual object). `assumed` = declared premise ⇒ claim only in conditional form. `tested` | `open` = gaps. `violated` ⇒ claim cannot be made as written.
- Claim state = `cannot` (a need violated, incl. derived; needs both sides of an exclusion; or a conflicting scenario) > `can` (every need verified) > `conditional` (rest assumed) > `open`. Verdict words (user ruling, round 2, every surface: GUI, CLI, export, engine labels + the proof naming `Can claim`) = Fully supported (can) / Conditional (conditional) / Pending verification (open) / Claim not possible (cannot) (user's set, chosen over MAIN's "Needs verification" + "Not possible as worded"); fact state `assumed` displays as "Assumed" (user ruling, round 2: the fact is assumed, the claim conditional).
- Conditional = reasoning verified (user ruling, round 2, supersedes the entailment ruling's "human-ruled entailment = assumed ⇒ at most On assumption"): a claim reads Conditional only when its entailment fact + every `result` fact it needs are verified (`proved` | `checked`); only premises (background conditions specific to the analysis, e.g. random assignment, independent samples) may stand as assumptions; otherwise Pending verification. A judgment mixed into a reasoning step → reword the claim to what can be proved, or split out a substantive, contestable premise (never one restating "the conclusion follows"). Universal premises (records honest, instruments working, labels right) are no claim's facts: the review sign-off vouches for them once (user ruling, round 2: listing them per claim = busy work). A claim that restates one checked result needs no separate reasoning fact (user ruling, round 2; engine still requires one → IMPLEMENT).
- Headline + exact statement (user request, round 2: claims too wordy): a claim shows a plain headline; its exact statement (= what the proofs cover, the claim `text`) opens on request ("Show the exact statement"; shown in full in its details). Rule: the headline never says more than the exact statement; the reviewer confirms that at sign-off.
- Entailment (user ruling: strict): every claim names one entailment fact ("these needs entail the sentence as worded"), counted as a need; the Conditional ruling sets how far an unproved one lets a claim rise.
- Evidence binding (user ruling): `proved` | `checked` require a receipt = artifacts (project-relative path + sha256) + verifier + statement + a digest of the fact's own content (an entailment fact's covers its claim's text + needs) ⇒ an artifact changed or missing, or the fact or claim reworded since pinning ⇒ effective status `stale` (unverified, shown beside the recorded status); `fvtrace pin` records digests; nothing is executed; receipts are accepted, not replayed (trusted base).
- Review: trace-level record (reviewer, date, digest of all content but the record) ⇒ `draft` (none) | `stale` (digest differs) | `reviewed`; every verdict of a draft or stale trace reads provisional; what-ifs are never reviewed evidence. Every surface shows the engine's sentence + label (recorded | what-if, review state, prospective qualifier); claim + fact texts appear verbatim.
- Subjects (user ruling): every fact + claim binds to a subject (the existing analysis or a dataset/analysis an experiment would create); an experiment's outcomes touch only its subject's facts ⇒ a new-data experiment lights sibling claims, never existing ones; cross-subject reuse = an explicit instantiation fact.
- Exclusions (user ruling): an exclusion = two facts that cannot both hold on one subject, itself carrying status + route + evidence; only a verified exclusion derives a violation (from a verified side); a recorded contradiction (asserted exclusion + both sides asserted) = `fvtrace check` error; a what-if asserting both sides ⇒ every claim on that subject reads Cannot claim (`conflicting what-if`); a claim needing both sides ⇒ cannot.
- Results + lints (user ruling): kind `result` = the observed value/pattern a claim asserts; `fvtrace check` warns per claim level (estimand, descriptive, inferential, causal, release) on missing roles, suppressed only by a recorded waiver with reason.
- Where FV pays = per closable fact (not violated): claims it gates + claims verifying it alone unlocks, ranked by unlocks; violated facts list apart as blockers (reword or new data). `latent` claims = overlooked directions.
- Experiments: `kind` `dry` | `wet`, `effort` hours < days < weeks < months, `success` (asserting statuses only) + `failure` (`violated` only) replayed as what-ifs on the experiment's subject, closed over `requires` + the creator of a prospective subject; per experiment `lights` (claims raised into can | conditional), `clears` (cannot → open), `breaks` (failure → cannot); ranked lights > clears > cheaper. A success touching a `result` fact reads "if this result is observed".
- Experiment outcome honesty (scientist-1 rulings): `checked` only via a proved checker on the actual data, `proved` only via a completed proof; empirical support → `assumed` at most; failure = established counterexample, inconclusive → `{}`.
- Plans (user ruling): per claim, a coherent experiment set (one subject, prerequisite-closed, no conflict) reaching the highest state the suggestions allow, cheapest by ordinal effort among those (exact search; above 20 relevant experiments the result is `tooLarge`, no plan claimed); alternatives per fact + remaining premises listed; labelled coverage, never scientific priority.
- Agent instructions (user ruling): portable Agent Skill embedded in the binary; `fvtrace skills install --agent claude|agents` writes the user-level skills dir by default; the host agent drafts the trace, `fvtrace check` validates, the user's review gates final verdicts; fvTrace never calls an LLM.
- Examples (user ruling): public = fvTrace's own trace (claims about fvTrace backed by its Lean proofs) + a synthetic study; the tau × amyloid trace lives outside the repo as a private local check against the veriformatics `studies/naoto` folder, carrying scientist-2's fixes (O11 split, O20, C6, result facts).
- GUI = claim diagrams (ITERATE approval): claims per question in verdict order, no verdict headings (user ruling, round 2: the heading repeated each card's verdict; new-data + overlooked groups keep theirs); a standout label heads every claim's words on cards, text view + details (user request, round 2): "Claim" + its verdict in the verdict's color (green Fully supported, amber Conditional, slate Pending verification, ink Claim not possible), then qualifiers + id/level quiet; the verdict line under the headline is gone (open finalists: A `/` = one filled tag "Claim: Conditional" | B `/?tag=pair` = ink "Claim" joined to the verdict on its wash); every verdict label outside the key reads "Claim: <verdict>" (user ruling, round 2; sentences that already say "claim" keep the bare word); "Assuming …" text view, experiments + plans, what-if; header = the `fvTrace` name alone (user ruling, GUI round 1: the "Claim circuits" subtitle removed); intro explainer = a titled "How this works" panel (user ruling, round 1, over numbered steps): "Each claim rests on facts. Its verdict comes from its weakest fact." + one key table (user ruling, round 2: two side-by-side legends = two paradigms; finalist A over two labelled keys): columns "Facts" | "Claims", each row = a fact state drawn with the diagrams' own symbol (Verified, Assumed, Open, Violated) + one-line meaning beside the verdict it gives as a claim's weakest + its meaning + its count; the verdict counts live there alone (no separate counts box); rows stack on phones; then how to suppose + select. No metaphor words (user ruling, round 2): no "lamp", "switch" or "circuit" in GUI copy → "a fact's symbol", "a claim's diagram", layout toggle "Diagrams | Text". Review state = one line under the study summary, never beside a verdict (user ruling, round 1: "(draft)" next to "On assumption" implied the two were related): "Not reviewed yet."
